# نظام إدارة المستشفى (HMS) — Enterprise Hospital Management System

نظام متكامل عربي أولًا (RTL) لإدارة العمليات الطبية والإدارية، مبني على PostgreSQL حقيقي مع **عزل بيانات على مستوى الصفوف (RLS)**، صلاحيات RBAC + ABAC، سجل تدقيق مقاوم للعبث، وسير عمل مريض كامل من الاستقبال حتى الفاتورة.

> البيانات المرفقة **اصطناعية بالكامل** (مرضى تجريبيون). لا تستخدم النظام لرعاية مرضى حقيقيين قبل مراجعة أمنية وامتثال مستقلة.

---

## 1) قرارات المعمارية (ADR مختصر)

| القرار | الاختيار | الأسباب | البدائل والمخاطر |
|---|---|---|---|
| المكدس | Node 22 + TypeScript + Fastify 5 + React 19/Vite | فريق واحد، أداء جيد، تحقق مخططات Zod، نظام أنواع end-to-end | NestJS (بنية أثقل)، .NET (شائع مؤسسيًا لكن لا يمكن التحقق هنا بنفس السرعة) |
| قاعدة البيانات | PostgreSQL (نفس SQL في التطوير والإنتاج) | معاملات ACID، قيود مرجعية، RLS، JSONB، توليد تقارير | MySQL (بلا RLS مكافئ)، NoSQL (غير مناسب للبيانات الطبية/المالية) |
| التشغيل في بيئة العرض | **PGlite** (PostgreSQL 18 WASM مدمج) | يمكن تشغيل واختبار SQL وRLS فعليًا داخل بيئة التجربة | الإنتاج: `DB_MODE=postgres` بنفس الترحيلات؛ PGlite أحادي الاتصال وغير مناسب للإنتاج |
| الوحدات | Monolith معياري (modular monolith) | حجم البيانات والاتساق أهم من مزايا الخدمات المصغرة | Microservices غير مبررة الآن؛ تُنقل وحدة المختبر/التكامل عند الحاجة |
| الجلسات | جلسات خادمية + Cookie httpOnly + CSRF | إبطال فوري، تحكم بالأجهزة، لا تخزين رموز في الواجهة | JWT بلا حالة أصعب في الإبطال |
| المصادقة | Argon2id + TOTP MFA + رموز استرداد | متوافق مع أفضل الممارسات | SMS OTP يعتمد على مزود غير مهيأ |

**حدود الثقة:** الواجهة لا تُصدّق أبدًا؛ كل تحقق على الخادم. كل عملية حساسة تُنفَّذ داخل معاملة `SET ROLE hms_app` + `set_config('app.facility_ids')` فتُطبَّق RLS حتى لو نسيت الواجهة/المسار تصفية.

## 2) التشغيل

```bash
npm install
npm run db:reset        # ترحيلات + بيانات تجريبية (PGlite)
npm run build
npm start               # http://localhost:8080
# تطوير الواجهة مع HMR: npm -w apps/web run dev   (proxy إلى 8080)
```
الإنتاج: `DB_MODE=postgres` + `DATABASE_URL` + مفاتيح `SESSION_SECRET`/`ENCRYPTION_KEY`/`SEARCH_HASH_KEY` (32 بايت base64). راجع `ops/` و`.env.example`.

**غير منفذ:** PACS/DICOM · الأصول والصيانة · الجودة/الامتثال · SNOMED CT · الترميز الكامل لـICD-10/LOINC.

## 4) الأمان والخصوصية

- **كلمات المرور:** Argon2id (19 MiB, t=2).
- **التشفير:** TLS في الإنتاج (reverse proxy) + AES-256-GCM على الحقول الحساسة (الهوية، الجوال، العنوان، رقم البوليصة) مع AAD يربط النص بالمستخدم/العمود؛ مفاتيح من البيئة (KMS/Vault في الإنتاج).
- **RLS:** جداول المنشآت محمية بسياسات `app.facility_ids`؛ بوابة المريض بدور `hms_portal` مقيد `app.patient_id`؛ اختبارات تمنع التجاوز.
- **الصلاحيات:** RBAC (25 دورًا، 98 صلاحية، 29 حسابًا تجريبيًا) + ABAC (علاقة علاجية للملف السريري، أو break-glass محدد المدة بسبب موثق وتنبيه إداري). لا يوجد «تجاوز مدير نظام»: حساب إداري لا يقرأ السجل السريري، وحساب الموارد البشرية معزول تمامًا عن سجلات المرضى.
- **CSRF** عبر رأس لكل طلب تعديل + فحص Origin، **Helmet/CSP**، **Rate limiting** (حد لصفحة الدخول)، **منع حقن SQL** (استعلامات معلمة فقط)، **تحقق مدخلات Zod** على كل مسار.
- **التدقيق:** `audit_log` بسلسلة hash (SHA-256 مرتبطة بالسابق)، مشفّرة الترتيب بقفل صف؛ UPDATE/DELETE ممنوعة بـ trigger وREVOKE. كل قراءة ملف تُسجل في `patient_access_log`. تحقق السلسلة متاح من `/api/audit/verify`.
- **الجلسات:** خادمية، مهلة خمول 30 د + حد مطلق 12 س، إبطال فوري، عرض/إبطال الجلسات، إعادة تعيين عند تغيير كلمة المرور، MFA عبر TOTP مع رموز استرداد.
- **النسخ/الاستعادة:** انظر `ops/` (RPO/RTO أدناه). لم تُنفَّذ اختبارات استعادة تلقائية هنا — يجب تنفيذها في بيئة الإنتاج.

**PDPL (السعودية):** التصميم يراعي مبادئ تقليل البيانات، تحديد الغرض، سجل الوصول، وحقوق الأفراد عمليًا — **لكن لا يوجد ادعاء بالامتثال القانوني أو أي اعتماد تنظيمي**؛ يلزم تقييم قانوني/أمني مستقل وتسجيل لدى الجهة المختصة قبل التشغيل الفعلي.

### النشر على Vercel (بيئة عرض جاهزة)

المشروع `hospital-hms` منشور على Vercel ويعمل بنفس كود الـAPI (Fastify) — كل `/api/*` تُوجَّه إلى دالة واحدة `api/index.ts`، والواجهة تُخدم كملفات ثابتة من `public/`.

- **الرابط:** https://hospital-hms-cyan.vercel.app
- **الحسابات:** نفس الحسابات التجريبية أعلاه (`@demo.hms`)، والبيانات تُزرع تلقائيًا عند أول تشغيل.
- **حسابات إضافية:** `nurse2@demo.hms` و`radiology@demo.hms` و`radiologist@demo.hms` و`surgeon@demo.hms` و`anesthesia@demo.hms` و`ornurse@demo.hms` و`intensivist@demo.hms` و`icunurse@demo.hms` و`bloodbank@demo.hms` و`dietitian@demo.hms` و`kitchen@demo.hms` (كلمات المرور في أعلى الملف).
- **الإعداد:** `NODE_ENV=production` · `COOKIE_SECURE=true` · `TRUST_PROXY=true` · `AUTO_BOOTSTRAP=true` · `SEED_DEMO=true` · `PGLITE_DIR=/tmp/hms-data` · وأسرار AES/HMAC بثلاثة مفاتيح `SESSION_SECRET` و`ENCRYPTION_KEY` و`SEARCH_HASH_KEY` (كل واحد base64 لـ32 بايت عشوائية؛ يتحقق منها `config.ts` برسالة واضحة).
- **قيود صريحة:** قاعدة PGlite داخل الدالة تعمل على `/tmp`، أي أنها **مؤقتة** وتُعاد تهيئتها عند إعادة تشغيل الدالة (cold start) أو تغيّر النسخة. لذلك تظهر لافتة صريحة في الواجهة، وهذا **ليس** بديلًا عن قاعدة إنتاج.
- **لجعلها دائمة:** اربط Postgres (Neon/Vercel Marketplace) واضبط `DB_MODE=postgres` و`DATABASE_URL` ثم أعد النشر؛ المخطط والهجرات والـRLS متطابقة.
- **إعادة النشر:** أي دفع إلى `arena/94f94536-hospital` + إنشاء نشر جديد؛ لا توجد أسرار في المستودع.

### جرّب وحدة التمريض (٥ دقائق)

1. ادخل بـ`nurse@demo.hms` / `Nurse#Demo2026` ثم افتح **التمريض** — يظهر سرير `MRN-0004` (العناية المركزة) مع الجرعة المتأخرة والمهام المستحقة.
2. اختر المريض → فعّل «تحققت من الهوية» و«راجعت الحساسية» → أعطِ **الباراسيتامول**؛ جرّب إعطاءه مرة ثانية فورًا لتظهر رسالة الفاصل الأدنى.
3. أعطِ **الوارفارين** (دواء عالي الخطورة): بدون شاهد يُرفض، وباختيار `ليلى العمري` (حساب `nurse2@demo.hms`) يُسجَّل الشاهد.
4. أنجز مهمة من خطة الرعاية، ثم اكتب تسليم مناوبة SBAR وسجّل استلامه من الحساب الثاني — النصوص لا تُعدّل بعد الحفظ.

### جرّب غرفة العمليات (٥ دقائق)

1. ادخل بـ`surgeon@demo.hms` / `Surgeon#Demo2026` وافتح **العمليات والتخدير** — العملية `SUR-000001` (استئصال مرارة بالمنظار) مجدولة اليوم.
2. افتحها وأكمل **قائمة ما قبل التخدير** بكل بنودها (يُرفض الحفظ إن نقص بند)، ثم سجّل **قائمة ما قبل الشق** وابدأ العملية.
3. ادخل بـ`anesthesia@demo.hms` / `Anesthesia#Demo2026` وسجّل قياس تخدير (نبض/ضغط/SpO₂/دواء) — السجل ملحق لا يُعدّل.
4. أغلق العملية بعد تسجيل عدّ الأدوات؛ عند اختلاف العدد يُرفض الإغلاق إلا بملاحظة تصحيحية موثقة تبقى ظاهرة كتحذير.
5. سجّل الإفاقة بدرجة ألدريتي ≥ ٨ لتكتمل العملية وتُنشأ فاتورة العملية (٣٥٠٠) والتخدير (١٢٠٠) تلقائيًا.

### جرّب العناية المركزة (٥ دقائق)

1. ادخل بـ`intensivist@demo.hms` / `ICU#Demo2026` وافتح **العناية المركزة** — المريض `MRN-0004` على سرير ICU مع SOFA = 3 ودعم HFNC بFiO₂ 40%، وحزمة الرعاية مسجلة اليوم.
2. افتح الملف وسجّل علامات حيوية جديدة (نبض/ضغط/SpO₂/GCS) — السجل ملحق ولا يقبل التعديل.
3. غيّر إعدادات التنفس (جرّب وضع «هواء محيط» مع FiO₂ 50% ليُرفض)، ثم احسب **SOFA** بعد إدخال PaO₂ وFiO₂ والصفيحات والبيليروبين وMAP وGCS والكرياتينين.
4. ادخل بـ`icunurse@demo.hms` / `ICU#Demo2026` لتعبئة حزمة الرعاية اليومية — لا يستطيع التمريض فتح إقامة جديدة ولا إغلاقها.
5. أغلق الإقامة بملاحظة ≥ ١٥ حرفًا؛ بعدها يُرفض أي قياس جديد وتُرفض إعادة الإغلاق.

### جرّب التغذية الطبية (٥ دقائق)

1. ادخل بـ`nurse@demo.hms` وافتح **التغذية الطبية** — المريض `MRN-0004` بخطورة «مرتفع» (نقاط ٦) وأمر تغذية سكري، و٤ صواني اليوم.
2. سجّل فحص تغذية جديدًا (وزن/طول) مع إجراء موثق؛ جرّب حفظه بلا إجراء مع نقاط مرتفعة ليُرفض. الفحص سجل ملحق لا يُعدّل.
3. ادخل بـ`dietitian@demo.hms` / `Nutrition#Demo2026`: احفظ تقييمًا (هدف ١٨٥٠ سعرة و٨٩ غ بروتين مقبول، وأي انحراف >٢٥٪ يحتاج سببًا)، ثم أصدر أمر تغذية — **سيُرفض** إن أغفلت قيدًا إلزاميًا من حساسية المريض.
4. اضغط «توليد وجبات اليوم» مرة واحدة (٤ صواني)؛ إعادة الضغط لا تُكرر الصواني.
5. ادخل بـ`kitchen@demo.hms` / `Kitchen#Demo2026`: حضّر صينية ثم سلّمها (لا تسليم قبل تحضير)، ثم سجّل بحساب التمريض نسبة الاستهلاك (لا استهلاك قبل تسليم، والصينية تصبح مقفلة).
6. جرّب أمر تغذية أنبوبية على المسار `ng` ثم أمرًا ثانيًا على نفس المسار (يُرفض)، وأوقفه بسبب ≥ ٥ أحرف.

### جرّب التعقيم ومكافحة العدوى (٥ دقائق)

1. ادخل بـ`cssd@demo.hms` / `CSSD#Demo2026` وافتح **التعقيم ومكافحة العدوى** — ٧ أطقم و٧ حزم: حزمة مصروفة للعملية `SUR-000001`، حزمة معقّمة مخزّنة، دورة فاشلة حجزت حزمتها، وحزم قيد الغسل/التعقيم.
2. استلم حزمة ملوّثة لطقم جديد، ثم غسلها وغلفها، وافتح دورة تعقيم باختيار الحزم المغلفة — لا تُفتح الدورة بحزمة غير مغلفة.
3. سجّل نتيجة الدورة «ناجحة»، ثم حاول **اعتمادها بنفس الحساب** (يُرفض: فصل مهام). ادخل بـ`cssd2@demo.hms` واعتمدها — تُفرج الحزم بصلاحية ٣٠ يومًا للتغليف و٩٠ للحاوية.
4. اصرف الحزمة من بطاقة «صرف حزمة معقّمة» مع ربطها بعملية، ثم سجّل استخدامها واسترجاعها؛ إعادة الاستلام تزيد عدّاد الدورة ولا تنشئ رقمًا جديدًا.
5. سجّل نتيجة «فاشلة» لدورة جارية: تُحجز كل حزمها ويمنع صرفها، ويُرفض اعتماد دورة لم تنجح. السحب المتأخر لدورة معتمدة يعرض العمليات المتأثرة.
6. بدّل إلى تبويب **مكافحة العدوى**: أنهِ العزل النشط بسبب موثّق، ثم أصدر عزلًا آخر، سجّل حالة عدوى مشتبهة، وادخل بـ`infection@demo.hms` / `Infection#Demo2026` لتأكيدها — لا يعتمد المُبلّغ حالته ولا يُغيّر قرارًا بعد الاعتماد.

**حدود التعقيم ومكافحة العدوى:** لا تكامل مع أجهزة التعقيم (المؤشرات تُدخل يدويًا)، ولا تتبع على مستوى الأداة داخل الطقم، والصلاحية افتراضية موثقة (٣٠/٩٠ يومًا). حالات العدوى أعداد وصفية بلا معدلات NHSN/CDC معدّلة، ولا كشف آلي لتفشي العدوى، والعزل قرار بشري موثّق. لا توجد مطالبة أو اعتماد من جهة رقابية.

**حدود التغذية:** لا قاعدة تراكيب غذائية ولا مخزون مطبخ ولا قائمة طعام؛ سعرات الصينية حصة ثابتة (٢٥/٣٥/٣٠/١٠٪) من هدف اليوم، وأهداف الطاقة/البروتين تقديرية حسب الوزن مع إمكانية انحراف مبرر. نقاط الخطر أداة فرز مستوحاة من NRS-2002 وليست جهازًا طبيًا معتمدًا.

### جرّب بنك الدم (٥ دقائق)

1. ادخل بـ`bloodbank@demo.hms` / `Blood#Demo2026` وافتح **بنك الدم** — المخزون 14 وحدة، والطلب `BLR-000001` لمريض فصيلته `A-` (كريات حمراء، وحدتان، عاجل).
2. افتح الطلب: تظهر كل وحدات الكريات المتاحة مع سبب الرفض للمتوافقة ظاهريًا فقط (`A+` مرفوضة للعامل الريصي، `B+` مرفوضة لـABO).
3. اضغط **فحص وحجز** على وحدة `O-` أو `A-` (يصبح عدد المحجوز 1)، ثم **صرف للجناح** من قائمة الوحدات المحجوزة — لا يمكن الصرف قبل فحص توافق ناجح.
4. ادخل بـ`nurse@demo.hms` / `Nurse#Demo2026`، افتح تفاصيل الوحدة المصروفة → اختر المدقق الثاني `ليلى العمري` وفعّل الموافقة ثم **بدء النقل**؛ جرّب اختيار نفسك أو حساب استقبال ليُرفض.
5. أغلق النقل بالحجم المنقول، ثم سجّل تفاعلًا (متوسط أو شديد يتطلب إغلاق النقل أولًا) — تتحول الوحدة إلى **مستبعدة** بسبب «تفاعل نقل» ولا تعود للمخزون. لا يستطيع الاستقبال رؤية أي من ذلك (403).

**حدود بنك الدم:** قواعد ABO/Rh جدول ثابت على الخادم (RBC: O→O, A→A/O, B→B/O, AB→AB/A/B/O؛ البلازما والراسب القري بالعكس؛ Rh سالب لا يستقبل موجبًا في الكريات والصفائح). لا فحص أجسام مضادة (screen/titre)، لا مطابقة إلكترونية تتجاوز الفحص، ولا تكامل مع بنك دم وطني أو مورّد. التجاوز الموثق يُسجّل قرارًا سريريًا لكنه **لا** يسمح بالصرف.

## 8) المخاطر المتبقية (مهمة)

1. **PGlite للتجربة فقط** — إنتاج يحتاج PostgreSQL مُدار وبنسخ احتياطي PITR.
2. لا مزود بريد/SMS/دفع/تأمين — يُوثَّق كـ«غير مرسل» ولا يُدّعى الإرسال.
3. FHIR تغطية جزئية وغير معتمدة؛ لا DICOM/PACS.
4. حداثة قاعدة الحقول المشفرة: البحث بالاسم غير مشفر (مقصود للبحث) — يلزم تقييم مخاطر وتشفير كامل عند الحاجة.
5. MFA اختياري افتراضيًا في العرض؛ يجب فرضه إداريًا في الإنتاج (`mfa_enforced`).
6. لا توجد صلاحيات مؤقتة متقدمة/تفويض وكلاء، ولا تكامل مع نظام الهوية المؤسسي (SSO).
7. اختبارات الأداء والأمن والاستعادة قبل الإنتاج إلزامية.
8. تغيير خوارزمية سلسلة التدقيق يبطل السجلات السابقة؛ لذلك أُضيف `hash_version` — أي تغيير مستقبلي يجب أن يبدأ مقطع سلسلة جديدًا لا أن يعدّل السابق.
